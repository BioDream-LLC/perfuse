# CMS-0057 for payers

The CMS Interoperability and Prior Authorization final rule (CMS-0057-F) requires impacted payers — Medicare Advantage organisations, state Medicaid and CHIP programs and their managed care plans, and QHP issuers on the federal exchanges — to run four FHIR APIs from 1 January 2027, and to post prior authorisation metrics on their public website every year from 2026.

Perfuse provides the four APIs on its FHIR endpoint and the conversions that fill them: adjudicated claims as CARIN Blue Button, prior authorisations as Da Vinci PDex, and the yearly metrics in the layout of CMS's own template. The **CMS-0057** view, under Exchange, says which of the four this instance can answer and what each still needs, and does all three conversions in the browser.

Drugs are out of scope throughout, as they are in the rule's prior authorisation provisions: no pharmacy claims, no formulary, and a metrics row naming a drug is refused rather than counted.

## The four APIs

| API | What it serves | Guides | Turned on by |
|---|---|---|---|
| Patient Access | A member's claims, clinical data and prior authorisations, to an app they choose | CARIN Blue Button 2.2.0, PDex 2.2.0, US Core, SMART App Launch | `-fhir` and a SMART issuer (`-smart-issuer`) |
| Provider Access | The same for a provider's attributed members, in bulk | PDex 2.2.0, Da Vinci ATR 2.1.0, Bulk Data | `-fhir-payer-apis` and `-fhir-bulk-export` |
| Payer-to-Payer | A member's record to another payer, after matching them | HRex 1.2.0 `$member-match`, PDex 2.2.0 | `-fhir-payer-apis` |
| Prior Authorization | What an order needs, the documentation, then the request and decision | Da Vinci CRD 2.2.1, DTR 2.2.0, PAS 2.2.1 with X12 278 translation | `-fhir`, writable, and `-crd-rules` |

The Patient Access API needs no operation of its own: it is the FHIR endpoint's ordinary read and search, protected by SMART, with CARIN and PDex resources in the store. Searching `ExplanationOfBenefit` supports the parameters CARIN names — `patient`, `identifier`, `type`, `service-date`, `billable-period-start`, `provider`, `insurer`, `coverage` — and `Coverage` supports `subscriber-id`, `identifier` and `payor`.

## Coverage requirements and documentation: CRD and DTR

The Prior Authorization API is in practice three Da Vinci guides together. **CRD** tells the clinician, while the order is still a draft,
whether it is covered, whether it needs prior authorisation and what documentation is wanted. **DTR** hands the EHR the questionnaire that
gathers that documentation. **PAS** submits the request and returns the decision. Perfuse serves all three as the payer.

`-crd-rules rules.yaml` serves CRD over CDS Hooks at `/cds-services`: the `order-sign`, `order-select`, `order-dispatch` and
`appointment-book` hooks, each with a prefetch for the patient's active Coverage. The rules are the payer's policy, kept in a file
because they change without software releases:

```yaml
payer: Springfield Health Plan
rules:
  - description: Home oxygen equipment
    codes: [E0424, E0431]
    covered: covered            # covered, not-covered, conditional
    pa: auth-needed             # no-auth, auth-needed, satisfied, performpa, conditional
    documentation: [clinical]
    questionnaire: https://www.springfield-health-plan.example/fhir/Questionnaire/home-oxygen
```

Each order gets a `systemActions` update carrying CRD's coverage-information extension - which the EHR stores on the order and later
sends on with the prior authorisation - and a card the clinician reads. An order whose code has no rule is answered `conditional`, never
assumed covered; a request with no Coverage at all gets a card saying so. `examples/crd/` has a rules file and a matching
questionnaire.

A rule can also carry the rest of what CRD lets a payer say:

- `billing_codes`: the codes to bill under.
- `details`: limits and costs, such as `allowed-period` or `in-network-copay`.
- `contact`: who to call.
- `expiry_days`: how long the answer holds.
- `depends_on`: codes of other orders the answer depends on, so the EHR asks again if they change.
- `doc_purpose`: what the documentation is for (`withclaim`, `withorder`, `retain-doc`). `withpa` is refused, because CRD 2.2.1's
  own invariant crd-ci-q4 rejects it.

What the EHR did not prefetch, Perfuse reads from the EHR's `fhirServer` with the token it sent. If that fails, the answer is
`indeterminate` with CRD's `technical` reason, never a guess. A Coverage that has ended or is not active is answered `not-covered`,
`no-active-coverage`.

`members: fhir` in the rules file resolves the coverage against the payer's own records in this server's FHIR store (start it with
`-fhir`), the same records `$member-match` reads:

- a patient who is not a member is answered `no-member-found`;
- a member whose coverage does not match is answered `coverage-not-found`;
- a prior authorisation already approved there for the service (a ClaimResponse with a `preAuthRef`) makes the answer `satisfied`,
  with that number.

Discovery declares `davinci-crd.version` and a `coverage-info` configuration option. When a client turns the option off, the answer
is empty. EHR JWTs are checked as CDS Hooks defines them, with `iss`, `aud`, `exp`, `iat` and `jti` and no `sub`, and a repeated
`jti` is refused.

Calls authenticate with the JWT an EHR signs for each call, from an issuer named in `-cds-clients` with its JWKS URL - which is how CDS
Hooks describes it - or with a Perfuse API token. Discovery is open, as CDS Hooks requires.

**DTR**: load the questionnaires into the FHIR endpoint, and `POST /fhir/Questionnaire/$questionnaire-package` returns them as DTR
package bundles, with the CQL Libraries they name. The request can name the questionnaire, or send the order and let its
coverage-information say which.

**Trying it**: Payers → Claims & auth → Coverage requirements (CRD) sends an order to this server's rules, or to a payer's CDS
service URL, and shows the cards and the coverage information.

## Claims as CARIN Blue Button

`perfuse cms0057 carinbb` pairs each claim in an 837 with its payment in an 835, by the patient account number the 835 is required to echo back, and writes a FHIR transaction for each: the ExplanationOfBenefit with the Patient, Coverage, Organizations and Practitioners it references.

```sh
perfuse cms0057 carinbb -system https://fhir.your-plan.org/identifier -network innetwork \
    claims.837 remittance.835
```

The profile follows the claim: professional claims (837P) become `C4BB-ExplanationOfBenefit-Professional-NonClinician`, and institutional ones (837I) inpatient or outpatient by the type of bill. Every entry is a PUT with an id taken from the source identifiers, so loading the same claim twice updates it rather than making a second copy.

Three things are not in either X12 file, and each is handled by saying so rather than by guessing:

- **The identifier system.** CARIN requires the member identifier to name the payer's namespace. `-system` is required; there is no default, because a default would give every payer using Perfuse the same namespace.
- **The network status.** Neither transaction says whether the billing provider is in network, and it decides what the member pays. Without `-network` the benefit payment status is `other` and the conversion notes why.
- **A claim the 835 does not mention.** A CARIN ExplanationOfBenefit is an adjudicated claim. Without the 835 there is no payer claim number, no payment and no member liability, so the claim is reported as skipped and not converted.

Diagnoses are written with their decimal point (`J02.9`, not `J029`), because that is how the code system publishes them and a terminology server asked about the other spelling says it does not exist. A dependent's member identifier is the subscriber's, which is what the 837 carries, and the notes say so. An NPI whose check digit is wrong is reported before US Core rejects it.

## Prior authorisations as PDex

`perfuse cms0057 priorauth` converts a Da Vinci PAS ClaimResponse — or the PAS response bundle that carries one — into a PDex prior authorisation ExplanationOfBenefit, which is what all three data APIs serve.

```sh
perfuse cms0057 priorauth pas-response.json pas-claim.json
```

The PAS Claim is optional and nearly always needed. An ExplanationOfBenefit must say which coverage the decision was made under, and only the request carries that; without it the conversion stops and says so. The review action — approved, denied, pended, with its authorisation number and reason — moves from PAS's extension to PDex's, and the X12 service type keeps its code under the URI PDex binds it to.

## The Provider Access and Payer-to-Payer APIs

With `-fhir-payer-apis` the FHIR endpoint answers three more operations:

- `POST /fhir/Patient/$member-match` — HRex member matching. The coverage identifiers narrow to a few candidates, and the family name and date of birth must then agree; a given name is compared by initial, and gender only when both sides state it. More than one surviving candidate is not a match, and the answer is 422 rather than a guess, because a guess discloses a stranger's claims. An active Consent permitting disclosure is required, since the Payer-to-Payer API is opt-in for the member; `-fhir-member-match-without-consent` turns that off for testing.
- `GET` or `POST /fhir/Group/{id}/$davinci-data-export` — the Da Vinci bulk export of a Group's current members. `exportType` chooses the audience: `hl7.fhir.us.davinci-pdex#provider-download` or `#provider-delta` for Provider Access, `#payertopayer` for Payer-to-Payer.
- `GET /fhir/Group/{id}/$export` — the standard Bulk Data group export, treated as Provider Access.

The exports apply the rule's exclusions on the way out. Claims lose the payment and every cost-sharing and remittance amount, and keep the services, codes, dates and providers; the CARIN profile is removed from `meta.profile` because the resource no longer meets it. Payer-to-Payer also leaves out denied prior authorisations. Members holding an active PDex Provider Access opt-out Consent are left out of a provider export, and the log records how many. The `patient` parameter can only narrow to members of the Group; naming anyone else is refused.

Access to a Group's export is decided by the endpoint's authentication. SMART scopes say what kinds of resource a token may read, not which Group, so each provider needs a token that can reach only its own attribution list. An API token can be limited to Groups when it is made — `perfuse token create -label riverside-provider-access -fhir-groups riverside-attributed`, or the **Limit to FHIR Groups** field under Users → Machine credentials — and on the FHIR endpoint it can then read those Groups, run `$davinci-data-export` or `$export` on them and fetch what the export produced, and nothing else. Another provider's Group answers not-found rather than forbidden, so a token does not learn which other attribution lists exist; every other request, member matching and ordinary search included, is refused. The limit applies to API tokens; a token from a SMART issuer carries no Group limit. When SMART is configured as well, API tokens
are refused unless **Settings → FHIR → Accept Perfuse API tokens beside SMART tokens** is on (see Security, *Who may call the FHIR
endpoint*); a provider's Group-limited token needs it.

## A provider directory: Plan-Net

CMS-0057 also asks payers for a provider directory, and the FHIR endpoint serves one to Da Vinci Plan-Net 1.1.0 with no option to
turn on: load the Practitioners, PractitionerRoles, Organizations, OrganizationAffiliations, Locations, HealthcareServices,
InsurancePlans and Endpoints, and members' apps can search them. Every Plan-Net search parameter is indexed - a role's network and
service, a plan's coverage area, an affiliation's participating organization, an organization's `partof` - along with the
includes and reverse chains (`_has`) the guide's queries use, and the CapabilityStatement lists the Plan-Net profiles.

Inferno's Plan-Net suite passes 199 tests. The 10 it fails are forward chains where the kit takes its search value from the first
Organization it has seen rather than one the searched resources refer to; that is reported to the kit (its issue 34), and the
server answers those queries correctly when given a value the data holds.

## Prior authorisation metrics

`perfuse cms0057 metrics` reads a CSV of decisions exported from the utilisation management system and produces the public page CMS requires, in the layout of its *Prior Authorization Metrics Reporting — Overview and Template*.

```sh
perfuse cms0057 metrics -year 2025 -org "Springfield Health Plan" -services services.csv \
    decisions.csv > prior-authorization-metrics-2025.html
```

Columns are found by header: `priority`, `received`, `decided` and `decision` are required, and `request_id`, `line_of_business`, `extended`, `appealed`, `appeal_decision`, `service_code` and `service_description` are read when present. A request belongs to the year it was decided in; one still pending is listed as excluded, never counted. Every row that cannot be read is reported with its line number.

The arithmetic follows the template: for standard and expedited requests separately, the share approved and denied, approved and denied within the decision timeframe, approved after the review time was extended, and approved after appeal — out of appeals, not out of requests — with the mean and median time from receipt to decision. A median under a day is written in hours rather than rounded to "0 days", which the template asks for explicitly. Partly approved requests are counted as approved, since the template has no category for them, and the page says how many there were. Metrics are reported per line of business, which is the level CMS requires.

The page is self-contained — no script, no external stylesheet or font — because it is posted on a public website by whoever maintains that, and anything it loads from elsewhere is something else that can break or track a visitor. `-format csv` and `-format json` give the same numbers for other uses. Without `-services` the page carries a notice that the list of items and services requiring prior authorisation is missing, because CMS requires it on the same page.

## Drugs: the formulary, Real-Time Prescription Benefit and electronic prior authorization

CMS-0062-P (proposed 14 April 2026) would bring drugs into prior authorization: impacted payers would support NCPDP SCRIPT
electronic prior authorization, the NCPDP Formulary & Benefit standard and NCPDP Real-Time Prescription Benefit from 1 October
2027, decide drug requests within 24 hours (expedited) and 72 hours (standard), give a specific reason for every denial, and
report drug metrics from 2028. Medicare Part D already requires SCRIPT ePA. One file, the formulary, answers all of it:

```sh
perfuse serve -fhir -pas -crd-rules payer-rules.yaml -formulary formulary.yaml
```

`examples/formulary/formulary.yaml` is a sample whose drugs are real RxNorm concepts with NDCs RxNorm lists for them (checked
against RxNav). A file names the payer, its plans (each with the formulary it uses, its group IDs and its cost shares by pharmacy
benefit and tier) and its formularies. Each drug is an RxNorm SCD or SBD with its RxNorm group (the SCDG or SBDG the Drug
Formulary API requires), its NDCs, a tier, and its limits: `prior_authorization`, `step_therapy`, `quantity_limit` (a quantity in
a rolling number of days, and a daily maximum), `not_covered`, `alternatives` (RxNorm codes, most preferred first), `notes`, and
`questionnaire`, the canonical URL of the FHIR Questionnaire a prior authorization asks. `cost_30_day` is the plan's cost of a
30-day supply, which a coinsurance is a percentage of; without it a coinsurance is quoted as a percentage, never as an invented
amount. The whole file is checked when it loads, every problem listed at once. A member is found by the file's `members` list,
by group, or through the FHIR store: a `Coverage` whose `subscriberId` is the member ID and whose `class` of type `plan` is the
plan's id. **Payers › Drugs** shows the formulary, prices a drug and runs a prior authorization end to end.

### The Da Vinci US Drug Formulary API

Published at `/formulary/fhir` as Da Vinci US Drug Formulary 2.1.0: each plan a `PayerInsurancePlan`, each formulary a
`Formulary` (both `InsurancePlan`), each drug a `FormularyDrug` (`MedicationKnowledge`) and each entry a `FormularyItem`
(`Basic`). The guide's searches are served (`Basic?code=formulary-item&formulary=...&drug-tier=...&pharmacy-benefit-type=...&period=...`,
`subject:MedicationKnowledge.code`, `InsurancePlan?formulary-coverage=...`, `coverage-type`, `MedicationKnowledge?code=...&doseform=...`)
with `_include=Basic:subject`, `Basic:formulary` and `InsurancePlan:formulary-coverage`. It is public, with no credential, as CMS
requires of a payer's formulary: it is served from a store of its own, in memory, that holds the formulary and nothing else, so
being open cannot reach a patient's record. It is read-only. An excluded drug is not published, since the API lists what a
formulary covers; RTPB and ePA still answer it as not covered. **Verified** with the HL7 FHIR validator against the guide's 2.1.0
package with terminology checked: every resource generated from the sample has no errors.

### Real-Time Prescription Benefit

`POST /ncpdp/rtpb` takes an `RTPBRequest` (NCPDP RTPB v13) with an API token of the operator role and answers an `RTPBResponse`
from the formulary: the coverage status, the formulary status, the member's estimated share and the plan's, and the coverage
restrictions, with up to five covered alternatives priced the same way. Restriction codes and the status each maps to follow NCPDP's
public RTPB Implementation Recommendations: `75` prior authorization required, `608` step therapy, `76` plan limits exceeded, `7X`
days supply over the plan limit (a drug not available by mail, say), `70` not covered, all *covered with restrictions* (`CR`) except
`70` (`NC`). A member with an approved prior authorization on file gets `CC` and `AB8`, as the Surescripts guide asks, so the
prescriber is not sent to ask again. A request that cannot be priced is `NotProcessed` with an NCPDP reject code: `52` for a member
not found, `E7` and `19` for a missing quantity or days supply. The pharmacy benefit is read from the request: a fill over 34 days is
a three-month supply, and pharmacy type `M` is mail order.

### Electronic prior authorization (NCPDP SCRIPT)

`POST /ncpdp/script` takes `PAInitiationRequest`, `PARequest`, `PAAppealRequest` and `PACancelRequest` with an API token of the
operator role, and answers each with its response:

| Request | Answer |
|---|---|
| `PAInitiationRequest` | `Closed` when none is needed: `CC` no prior authorization required, `FN` within the quantity limit, `FM` not covered or not on the formulary, `FQ` an approval on file, `CD` no such member, `CG` one already in process. Otherwise `Open`, with a case ID and the question set. |
| `PARequest` | Decided as a PAS request: `Approved` with the authorization number and period, `Denied` with the reason, or `Open` under review. |
| `PAAppealRequest` | A denied case decided again, on the reason in `PANote` (an appeal without one is asked for it). |
| `PACancelRequest` | `Approved` while the case is open or under review, and the PAS request is cancelled; `Denied` once it is decided. |

The question set is the drug's FHIR Questionnaire from the FHIR store, the same one DTR fills in: a boolean becomes a yes/no choice,
a choice a choice, a number numeric, a date a date, and anything else free text; groups are flattened in order, and `enableWhen`
is not carried, since SCRIPT branches by choice and not by condition. A drug with no questionnaire is asked three free-text questions:
the diagnosis, what was tried, and why this drug. A `PARequest` becomes a Da Vinci PAS request: a `Claim` for the drug (RxNorm and
NDC), the `MedicationRequest` it asks for, the patient, prescriber, payer and coverage, and the answers as a `QuestionnaireResponse`,
with any attachments as `DocumentReference`s. It is then decided as every prior authorization on this server is: the rules file, a
decision service (`-pas-decider-url`), or the reviewer queue, where it is marked **Drug** and held to the drug timeframes. A decision
service sees a drug request exactly as it sees one from an EHR's PAS client. We recommend Vaglio, BioDream's source-available
(PolyForm Shield) decision engine, which has drug policies with step therapy; a payer's own engine plugs in through the same
`-pas-decider-url`, and none is needed for the rules file and reviewers to decide.

A decision made after the request was answered (a reviewer's, an appeal's) is sent to the prescriber as an unsolicited `PAResponse`
or `PAAppealResponse`, routed to the channel named by `-epa-reply-channel`, which delivers it to the network. Without one, or when
delivery fails, the case says the prescriber has not been told and the screen sends it again.

**Payers › Drugs › Prior authorization** sends the messages a prescriber's system would to this server's own endpoint (start, answer
the questions, see the decision), lists every case with what the prescriber was told, and shows the drug figures CMS-0062-P proposes:
requests approved, denied and pending, appealed and approved or denied on appeal, the mean and median hours from request to decision,
and how many were decided late. Medical-benefit drugs requested through PAS (a HCPCS J code with a `MedicationRequest`, or an item
coded in RxNorm or NDC) are counted as drugs in the PAS figures too.

**What this rests on, stated plainly.** NCPDP's schemas and implementation guides are licensed. The element names and order here
follow the public Surescripts ePA and RTPB companion guides and their examples, and NCPDP's public RTPB recommendations. Two
elements the public material never shows are written to the SCRIPT pattern used elsewhere and should be checked against a licensed
copy before certification: `Closed/ReasonCode` and `Denied/DenialReason`. No message has been checked against NCPDP's XSD or a
network's certification. The NCPDP Formulary & Benefit file is not produced: its full layout is in NCPDP's licensed guide, and
a partial file would be refused by the network that loads it.

## What was checked, and against what

The CARIN and PDex outputs were validated with the official HL7 FHIR validator, loaded with the published packages (`hl7.fhir.us.carin-bb#2.2.0`, `hl7.fhir.us.davinci-pdex#2.2.0`): professional, inpatient and outpatient claims and two PAS decisions, with no errors. The PDex inputs were the PAS guide's own examples rather than shapes written here to agree with the converter. The validator found five defects on the first run — among them that CARIN requires the profile version in `meta.profile` and the claim-type code system version on institutional claims — and each is fixed and covered by a test.

Building this found a defect older than it: the FHIR store dropped every element its internal model did not declare, so an ExplanationOfBenefit lost its items, diagnoses, adjudication and payment on the way in. The store now keeps whatever a resource carries, and a test loads a CARIN claim through the server and reads it back whole.

CRD's output - the updated order, and the CDS Hooks response against CRD's own logical model - and DTR's package output validate in the
official HL7 validator against CRD 2.2.1 and DTR 2.2.0 with no errors.

DTR here is the payer's side of 2.2.0. `$questionnaire-package` takes the questionnaires named, those CRD named on an order, or the
coverage assertion id CRD returned (`context`, while the same process is serving CRD), and returns each as a package bundle with a
QuestionnaireResponse to fill in, the Libraries its CQL needs and their dependencies. The value sets its answers use travel
in the package when they are loaded (`PUT /fhir/ValueSet/{id}`), and `$expand` lists their codes. `$log-questionnaire-errors` writes
what a DTR app reports to the server log.

**Adaptive questionnaires**: write the whole questionnaire once, with SDC's `questionnaireAdaptive` extension and `enableWhen` on the
questions that only apply sometimes. The package hands the app an empty shell, and each `$next-question` call adds the next question
that applies to the answers so far, until there is nothing left to ask and the response is marked completed. The order and the
branching are the payer's own rules; questions that do not apply are never shown.

**Signing in as a client**: DTR and PAS clients reach the payer with SMART Backend Services - a signed JWT exchanged for a token at
the payer's authorization server. Point Perfuse at that server with `-smart-issuer` (and `-smart-jwks` if its address does not resolve
from Perfuse), and pass `-smart-backend-services` so the discovery document says so. The Inferno DTR suite passes this way with
Keycloak as the authorization server.

Perfuse can be that authorization server itself: `serve -fhir -smart-clients clients.yaml` issues Backend Services tokens at
`/auth/token` to the clients listed, each with the public keys it signs its assertions with and the system scopes it may be
granted, and the FHIR endpoint accepts them. No separate identity server is needed for a payer's machine-to-machine clients.

With `-smart-users users.yaml` as well, members and clinicians sign in there to authorize apps, which the Patient Access API needs:
the app sends the person to `/auth/authorize`, they sign in, a clinician chooses the patient, and both see what the app asks for
and can untick any of it. A member is only ever given their own record, whatever the app asks for. Each person in the file names
the FHIR resource they are, `Patient/…` or `Practitioner/…`, and a password hash from `perfuse smart hash`; the password itself is
never written down.

People can sign in at the organisation's own identity provider instead: `-smart-oidc oidc.yaml` names it (issuer, client id and
where the secret is), and the sign-in page offers "Sign in with" it beside the password. Each person is linked by the
provider's subject, `oidc_subject` in the users file, so the file still decides who may authorize apps and which FHIR resource
they are; an account linked to nobody is refused. Codes, refresh tokens and revocations are kept in the database, so a restart
signs nobody out.

**Users → SMART apps** in the console lists the registered apps and the people, and adds, edits and removes them. Each save is
checked as the files are at start-up, written to them, and used at once. A confidential app saved without a secret is given one,
shown once; a password is set there and never shown back. Removing an app, or a person, stops the access tokens already issued
to it or granted by them at once, not when they expire, and their refresh tokens with them.

Scopes may be granular, as SMART App Launch 2 and US Core define them: `patient/Observation.rs?category=laboratory` reads only the
Observations that search would find. A grant that is filtered for a type applies its filter to every search and every read of that
type; an unfiltered grant for the type, or for `*`, lifts it. A filter that cannot be read grants nothing rather than everything.

## Deciding prior authorisation requests: PAS

`serve -fhir -pas -crd-rules rules.yaml` answers Da Vinci PAS 2.2.1 at `POST /fhir/Claim/$submit` and `POST /fhir/Claim/$inquire`.
The decisions come from the same rules file as CRD's answers, so the order a clinician is told needs authorisation is decided by
the rule that said so:

```yaml
  - description: Physical therapy
    codes: ["PT"]                       # matched on the item's productOrService, then the code of the order it requests
    system: https://codesystem.x12.org/005010/1365
    covered: covered
    pa: auth-needed
    pa_decision: approve                # approve, deny or pend; empty: not-covered is denied, no-auth approved, the rest pended
    details:
      - {code: allowed-quantity, value: "6"}   # asked for more, it is certified for six (A6, with the authorised detail)
  - description: MRI
    codes: ["62"]
    pa_decision: approve
    pa_alternative: {system: "https://codesystem.x12.org/005010/1365", code: "4"}  # approved as an X-ray instead (an added item)
  - description: Surgery
    codes: ["2"]
    pa: auth-needed                     # pended for a reviewer, asking for:
    questionnaire: https://payer.example.org/Questionnaire/surgery   # a DTR questionnaire
    pa_attachments: ["18776-5"]         # and documents, by LOINC attachment code
```

Each item gets an X12 review action: A1 certified, A3 not certified, A4 pended, A6 modified, C cancelled (certification type 3). A line
that names no service is not decided but answered with an error (X12 901 `AG`, correct and resubmit). The response echoes what a 278
response echoes — item trace numbers, the requested service dates, the encounter's dates, the transmission identifiers with sender and
receiver swapped — and gives each line the payer's own administration reference number. A service no rule names is pended, never
approved: a decision nobody wrote down is a decision for a person.

**Pended requests** wait for a reviewer, who answers with `POST /fhir/Claim/$decide`:

```json
{"resourceType": "Parameters", "parameter": [
  {"name": "claimResponse", "valueString": "<the ClaimResponse id>"},
  {"name": "decision", "valueCode": "approve"},
  {"name": "reason", "valueString": "Reviewed with the plan of care."},
  {"name": "reviewer", "valueString": "<the reviewer's NPI>"}]}
```

`decision` may also be `modify`: certified, but not as asked, with `quantity` (valueDecimal, the units certified) and/or
`alternative` (valueCoding, the service approved instead). The response then says A6 Modified, with the certified detail or
the alternative as an added item, and an authorization number. `item` (valueInteger, repeatable) limits the decision to some lines. The decision becomes a new version of the response, marked as
reviewed by a person, and with `-fhir-subscriptions` it is delivered on the PAS topic (`PASSubscriptionTopic`, filtered by
`org-identifier`, the requesting organisation's identifier) as the full PAS Response Bundle, in the same transaction that records it.
`$inquire` returns the current response to every request that provider made about that member; another provider's inquiry finds
nothing. `$decide` needs a write scope; `$inquire` is a read.

Requests and every version of their responses are kept in `pas_requests` and `pas_responses` in the server's database.

### The reviewer queue

In the web console, **Payers → CMS-0057 → Reviewer queue** lists the pended requests soonest due first: an expedited request
(Claim.priority `stat`) is due 72 hours after it arrived, a standard one 7 days. Choosing one shows the member, the provider, each
service with the units asked for and where it stands, what the response asked for, and every document received for it, with
plain-text documents shown inline. An editor records the decision there: approve, deny, or modify (units certified, or another
service approved instead), with a reason and the reviewer's NPI. A modification has to certify fewer units than were asked for;
as many or more is an approval, and is refused as a modification. A service approved instead starts in the code system of the one
asked for. It is the same decision `$decide` makes, so the provider's subscription delivers it. Reading a request and deciding it
are both written to the audit log.

**Monitor → Team dashboards → Prior authorization** shows, for the last 30 days, how many standard and expedited requests were
decided within CMS-0057's timeframes, decided late, still waiting in time and overdue now, with the median time to decide, and how
the services asked for were answered: approved, modified, denied or still pended. These two tiles are read from the requests
themselves, so they are not in the dashboard's Grafana export, which says so in its description.

### Receiving the documents a pended request asks for

A pended response asks for documents with a Task and one CommunicationRequest per document. The provider sends them with Da
Vinci CDex `$submit-attachment` (`POST /fhir/$submit-attachment`): the `TrackingId` is the CommunicationRequest's identifier, the
attachment control number (the Task's identifier is accepted too), `AttachTo` is `preauthorization`, and `MemberId` must be the
request's member. Each attachment's DocumentReference or QuestionnaireResponse is kept with the request and shown to its
reviewer; a document arriving decides nothing.

### Deciding in an X12 utilization management system

Most payers decide prior authorizations in a UM system that speaks X12 278. With `-pas-278-url`, Perfuse is the FHIR front of
that system: each `$submit` is sent as one 278 request (005010X217), every item a patient event. Each carries what PAS names for
it: the review type (`extension-serviceItemRequestType`, UM01: health services, admission or specialty care), the certification
type (`extension-certificationType`, UM02), the service type, the place of service (UM04), the level of service
(`extension-levelOfServiceCode`, UM06: elective, urgent or emergency; a `stat` priority stands in for urgent), the date, an
admission review's admission and discharge dates, the diagnoses, the care team's provider who will do the service, and the
procedure and quantity, as a professional (SV1) or, on an institutional claim, a hospital (SV2) service line. The 278 response's
action code and authorization number become the item's review action: certified, in part or modified, denied, pended,
cancelled, or not considered (pended for a reviewer, with the reject reasons). Local rules are not consulted.

```sh
perfuse serve -fhir -pas -pas-278-url https://um.example/x12/278 -pas-278-receiver ACMEUM \
  -pas-278-token-env UM_TOKEN
```

A UM system that pends first and decides later posts its later 278 response to `POST /fhir/Claim/$decide-278`; each event is
matched to its request by the trace number Perfuse sent, and decided as `$decide` would decide it. If the UM system cannot be
reached, or answers with something that is not a 278 response, every item is pended for a reviewer and the provider is told
only that; the reason is in the server log.

#### How the 278s reach the UM system

The UM system's connectivity guide says how it takes 278s, and `-pas-278-transport` (Settings, Payers, Utilization management
link) follows it:

| Transport | What is sent | Authentication |
|---|---|---|
| `x12` (default) | The 278 POSTed as `application/edi-x12`; the answer is the response body | A bearer token, OAuth, HTTP Basic, a client certificate |
| `core-soap` | The CAQH CORE real-time SOAP 1.2 envelope (`COREEnvelopeRealTimeRequest`, payload type `X12_278_Request_005010X217E1_2`): Connectivity Rule vC2.2.0 with the payload in the envelope, which most payers and CMS esMD run, or `-pas-278-core-version C4.0.0` with the payload as an MTOM attachment | vC2.2.0: a user name and password (WS-Security UsernameToken) or a client certificate. vC4.0.0: a client certificate and an OAuth token |
| `core-mime` | The CAQH CORE vC2.2.0 HTTP MIME multipart envelope, the payload as a file part | The envelope's UserName and Password, or a client certificate |
| `sftp` | Each 278 put in a folder on the UM system's SFTP server (`-pas-278-sftp`, `-pas-278-sftp-outbound`); its answers collected from another (`-pas-278-sftp-inbound`, every `-pas-278-sftp-every`) | An SSH key or password; the server's key must be in `-pas-278-sftp-known-hosts` |

A client certificate is `-pas-278-cert` and `-pas-278-key`; `-pas-278-ca` trusts a payer's own certificate authority. OAuth is
`-pas-278-oauth-token-url`, `-pas-278-oauth-client-id` and the secret, fetched with the client-credentials grant and kept until a
minute before it expires. Passwords, tokens and secrets are never flags: each is named by an environment variable
(`-pas-278-password-env`, `-pas-278-token-env`, `-pas-278-oauth-secret-env`, `-pas-278-sftp-password-env`), or typed into the
settings screen, where it is kept in the settings file (readable by the server's account only) and never shown again.

```sh
UM_PASSWORD=... perfuse serve -fhir -pas -pas-278-transport core-soap \
  -pas-278-url https://um.example/CORE/RealTime -pas-278-receiver ACMEUM \
  -pas-278-user perfuse -pas-278-password-env UM_PASSWORD
```

Over SFTP every request is pended until its answer arrives: the 278 response decides the items, and Perfuse puts a 999 accepting
it in the outbound folder. A file it cannot read stays in the inbound folder for a person, and is offered again at the next read.

#### When the UM system cannot read a request

A UM system that cannot read a 278 answers with a TA1 (the envelope) or a 999 (the transaction) instead of a decision. Perfuse
reads which and what it says, pends every item ("utilization management could not read the request"), and records it.
Payer, CMS-0057, Reviewer queue shows the link: what was sent in the last seven days, each interchange by its control number,
and what became of it (answered; acknowledged, answer to come; rejected, with the 999's segment, element and code; not reached).
Each interchange has its own control number, one more than the last, which is what a TA1 or 999 names when it answers.

### Deciding on the clinical evidence, with a decision service

A rules file decides by service code: a code needs no authorization, is not covered, or goes to a reviewer. Whether this patient
meets the criteria for it is a different question, answered from the conditions, questionnaire answers and documents the provider
sent with the request. With `-pas-decider-url`, every item the rules leave to a reviewer is first put to a decision service, such
as Vaglio, which reads the same PAS request Bundle through Perfuse's published `pas` package. A public Vaglio, on invented
requests only, runs beside Perfuse's test instance at https://vaglio.perfuse.health:8443 (sign in as `demo`, password
`try-vaglio-demo`; it can look at everything and change nothing): every decision there has its proof, a plain-language letter and a
receipt anyone can check.

```sh
perfuse serve -fhir -pas -crd-rules payer-rules.yaml -pas-decider-url https://vaglio.example/api/pas/decide \
  -pas-decider-token-env VAGLIO_TOKEN
```

The URL must be https, or plain http to this machine (`localhost`, `127.0.0.1`), because it carries a patient's record and the
token. Vaglio itself answers on https only; when it uses a certificate from its own authority, pass that authority with
`-pas-decider-ca DATA/tls/ca.crt` (or any payer's internal authority the service's certificate comes from). The service is sent the request Bundle as the provider sent it, `POST <url>?item=<sequence>` (`application/fhir+json`), and answers
`{"decision": "approve" | "deny" | "pend", "why": "...", "requested": ["..."]}`, or `404` when it decides nothing for that item, which
leaves the rules' answer standing. `why` is the response's process note and is required for a denial, which is otherwise pended;
`requested` is said to the provider as the information a pended request needs. A pend may also carry `"questionnaire": "<canonical>"`
and `"attachments": ["<LOINC>", ...]`, which are asked for in the response's CDex Task and CommunicationRequests beside whatever DTR
questionnaire or attachments the rule asks for (the rule's questionnaire wins, since a Task asks for one; a code that is not LOINC's
shape is dropped and logged). A rule that approves or denies is the payer's coverage policy and is not sent to the service. A failure, a timeout or
an answer that is not one of the three decisions pends the item for a reviewer, with the reason in the server log: nothing here turns
a failure into an approval. It cannot be combined with `-pas-278-url`, where the UM system answers every item.

**Advice before submitting.** With `-crd-advisor-url` beside `-crd-rules`, CRD also asks a decision service what a prior
authorization request for each order needing one would be told as the record stands, and shows the answer as one more card:
"Before you submit: a request for this would need: ...", or "would be approved", with what is still needed, the questionnaire that
asks for it, and what would approve it. Vaglio answers at `/api/pas/advise`, with the same token and authority as above:

```sh
perfuse serve -fhir -pas -crd-rules payer-rules.yaml \
  -crd-advisor-url https://vaglio.example/api/pas/advise -crd-advisor-token-env VAGLIO_TOKEN
```

CRD sends `POST <url>` with `{"service": {"system": "...", "code": "..."}, "resources": [ ... ]}`, the resources being the hook's
prefetch (the patient first, the coverage left out), and reads `{"decides": true, "answer": "approve" | "pend" | "deny", "summary":
"...", "missing": [...], "questionnaire": "...", "toApprove": [[...]], "policyTitle": "..."}`. It is advice and changes nothing:
the coverage-information, the other cards and the PAS decision are what the rules say. It waits at most three seconds, and no
answer, a failure, or `"decides": false` leaves the response exactly as it is without it. Perfuse never needs a decision service.

The request carries `X-PAS-Request-Id`, the id the response is known by. A service with its own reviewers that pends an item can
send their decision later as any reviewer's is sent: `Claim/$decide` with that id as `claimResponse`, the item's sequence, and the
decision and reason. The provider's subscription delivers it as it would one made in the reviewer queue.

A subscription with `id-only` content tells the provider which answer changed without saying what it is: the notification's focus
is `Bundle/<id>`. `GET /fhir/Bundle/<id>` returns the latest PAS Response Bundle, `GET /fhir/Bundle/<id>/_history/<n>` the version a
notification sent, and `GET /fhir/ClaimResponse/<id>` the ClaimResponse alone. A token bound to one patient is told they do not
exist, as for any record outside its patient.

**Verified** with the official Inferno PAS Server v2.2.1 suite (see verification). Not sent, though PAS marks them must-support:
`ClaimResponse.adjudication` with a review action, `ClaimResponse.extension:authorizedProvider` and
`ClaimResponse.item.extension:communicatedDiagnosis`, because the extensions they need are not allowed there by their own context in PAS
2.2.1 and the validator rejects a response carrying them; and `request.extension:DataAbsentReason`, because Perfuse always knows the
request. The 278s sent to a utilization management system (above) are checked against PAS 2.2.1's own request examples, CMS's
published esMD 278 samples and a 278 checker written from public companion guides, and every transport against a stand-in UM
system written from CAQH's Connectivity Rules (see verification); not yet against a real UM system or clearinghouse, and not
CORE certified. Not implemented: attachments sent back with CDex.

A rules file is checked against CRD's own invariants when it loads: a questionnaire needs documentation, a service that is not covered
cannot need authorisation, `satisfied` belongs to one case and not a rule, and anything conditional must give a reason.

Not verified: the exports and member matching against another payer's implementation, the metrics against a payer's published figures,
and CRD against a real EHR's CDS Hooks client.

## CMS Aligned Networks

The CMS Interoperability Framework (CMS Health Technology Ecosystem) asks health data networks to self-attest to 26 criteria and be
listed as **CMS Aligned Networks**; EHRs, providers, payers and apps connect to them. Criteria 13 to 16 have been in effect since
4 July 2026: FHIR APIs on US Core with a full CapabilityStatement and Bulk Data, documents as human-readable FHIR attachments,
appointment and encounter notifications by FHIR Subscription, and a record locator.

**Administer › CMS Aligned Network** lists every criterion with what Perfuse provides for it and where this server stands, read
from what is switched on here:

| Status | Meaning |
|---|---|
| Ready here | Perfuse provides it and it is on. |
| Ready, with a gap | It is on, and part of the criterion is outside it (named on the screen). |
| Built, not on | Perfuse provides it; the screen names the setting or flag that turns it on. |
| Yours to do | The organisation's part: an agreement, a certification, publishing to the National Provider Directory. |
| Not built | Software would do it, and Perfuse does not. |

What the four in effect need from this server:

| Criterion | In Perfuse | Turn on |
|---|---|---|
| 13 FHIR APIs, US Core, Bulk Data | The FHIR endpoint with its CapabilityStatement, and `$export` | `-fhir`, `-fhir-bulk-export` |
| 14 Documents as FHIR attachments | DocumentReference with Binary, and IHE MHD over the XDS registry | `-fhir` (MHD also `-xds`) |
| 15 Encounter and appointment notifications | Topic-based Subscriptions (R5 Backport for R4) from ADT and SIU feeds | `-fhir-subscriptions` |
| 16 Record locator | The XDS.b registry, XCA for other communities, PIXm | `-xds`, `-xds-home-community` |

The screen is a worksheet for the attestation, not a certification: CMS reviews networks it suspects do not meet the criteria, and
the framework's own text is the authority. Not built today: open quality gap queries (criterion 8), a payer's query for a claim's
encounter data (9), reporting query metrics to the National Provider Directory (19), checking providers against that directory
(6), reading mobile driver's licences or digital insurance cards (3, 23), and enforcing a general consent policy on every read
(5). IAL2 identity proofing is the identity service's; Perfuse accepts the tokens of the one you choose.
