Platform

An engine, a builder and a control room, in one program

Hospitals run dozens of systems that each speak their own dialect. An integration engine sits in the middle and translates. This page explains each part of Perfuse: what it is, why it exists, and how you use it.

The integration engine

Channels: one job each, done reliably

What it is

A channel is one interface: "take admissions from the hospital system and send them to the lab". It receives a message, checks it, changes it if needed, and delivers it to one or more places.

Why it exists

Without an engine every pair of systems needs its own custom link. With twenty systems that is hundreds of links, each failing in its own way at three in the morning.

How you use it

Pick where messages come from, where they go, and what should change on the way, in the browser or in a short text file. Perfuse does the rest and keeps a record.

  • Every destination has its own queue on disk, so one slow receiver never holds up the others
  • Messages are delivered in order, and retried with back-off, and a message that cannot be delivered is kept, never deleted
  • The sender is told "received" only after delivery, unless you choose otherwise
  • Every message is stored as it arrived, so it can be searched, compared and sent again

Channel builder

Build interfaces by answering questions

What it is

A guided form in the console. It asks where messages come from in plain words ("A sender connects to us over MLLP", "We read from an IBM MQ queue") and only shows the settings that apply.

Why it exists

Most interface changes are small: a new field, a code mapped differently, a second destination. They should not need a programmer.

How you use it

Open Channels, choose New, answer the questions, try it in the playground, then save. The result is a readable file you can keep in Git.

  • Eleven declarative steps: set, copy, remove, clear, default, case, date, pad, trim, replace and map, each with an optional condition
  • Shared mapping tables, with a record of who decided each mapping and why
  • JavaScript, including Mirth's dialect, or sandboxed Lua, when a step is not enough
  • Fields shown by name ("the patient's family name"), not only by position (PID-5.1)

Monitoring and alerts

A control room for every interface

What it is

A live dashboard, a flow map, metrics, team dashboards and alerts, built into the console.

Why it exists

Most interface outages are noticed by a nurse or a billing clerk, hours late. An engine should notice first and say so.

How you use it

Open the dashboard. Set alert rules once (error rate, no traffic, queue age and more), and send them to email, chat or your paging system.

  • Eleven alert kinds, including "quieter than usual", which catches a half-broken sender a fixed threshold misses
  • Team dashboards for operations, partner connections, prior authorization, imaging, revenue cycle, lab and privacy
  • Metrics for Prometheus and Grafana, and tracing over OpenTelemetry
  • A fleet view across several Perfuse servers, sharing counts only, never patient data

Changing live interfaces

Change a working interface without guessing

What it is

Shadow mode runs a new version of a channel beside the live one on real traffic, delivering nothing, and shows field by field where the two differ.

Why it exists

Test messages never contain the odd cases real traffic does. The only safe test of a change is the real feed, without the risk.

How you use it

Start a shadow from the channel's page, let it run for a day, and read the differences. When there are none you did not intend, promote it.

  • Feed contracts: write down what a feed should contain and be told the day a sender changes it
  • perfuse profile reports what a feed really contains
  • perfuse compare proves two engines agree on the same traffic
  • Channel history read from Git: what changed, when, and by whom

Security and sign-on

Built for patient data from the first line

Health data is the most sensitive data most organisations hold. Perfuse refuses to serve it over plain HTTP to anything but the machine itself, and records who looked at what.

ICON:users

Single sign-on

SAML 2.0, OpenID Connect and LDAP or Active Directory, tested against Keycloak and Microsoft Entra. Configure SAML by pasting your provider's metadata.

ICON:key

Passkeys

Sign in with a fingerprint, a face or a security key: nothing a fake login page can capture.

ICON:shield

Roles and audit

Six roles, from a monitor who sees status but no message contents to an operator who can resend but not edit. API tokens for machines, and an audit log of every change and every patient search.

ICON:layers

Channel groups

For a hospital group on one engine: limit a person to their facility's channels, and they see only those, in every list, chart, alert and search. Their own administrator manages their own people.

ICON:eye

Privacy monitoring

Each feed is compared with its own history for bursts, night traffic on daytime channels and new destinations, and the audit trail for one person reading many patients, all raised as alerts. Sign-in attempts are rate-limited.

ICON:server

Provisioning

SCIM 2.0, so your identity provider creates and removes accounts by itself.

ICON:plug

Mutual TLS

Certificates both ways on any connection, checked against OpenSSL rather than against our own client.

Always on

When one server stops, another carries on

Two or more servers share one PostgreSQL database and agree, through it, which of them runs each feed. A server that crashes or loses the database stops its feeds by itself; another starts them within about one lease, 15 seconds by default.

ICON:server

Active-passive or active-active

One leader running everything with the others standing by, or the feeds spread over every server and moved by hand from the console.

ICON:check

Nothing acknowledged is lost

Tested by killing the server running a feed, cutting it off from the database and running clocks minutes apart, on Linux and Windows behind an AWS load balancer: 16,000 acknowledged messages, none lost.

ICON:layers

One configuration

Channels, settings, alert rules and sign-on files are kept the same on every server; a change on any one reaches the rest in seconds.

ICON:chart

Monitored the usual way

A health check for the load balancer that says where each feed runs, Prometheus metrics, OpenTelemetry traces, and a read-only SNMP agent with alert traps for tools that speak SNMP.

The UK and Europe

Built for the GDPR, national numbers and national code systems

The console in twelve languages, the patient numbers and code systems each country uses, a person's data protection rights answered from one screen, and data that stays in the region it must. New in v0.1.18.

ICON:globe

Twelve languages

English, German, French, Dutch, Spanish, Italian, Portuguese, Polish, Swedish, Danish, Norwegian and Finnish, with each locale's dates and numbers; the manual too. Translated by machine, and says so until native speakers have reviewed it.

ICON:users

National patient numbers

The NHS number, CHI, KVNR, BSN, the French INS, codice fiscale, the Nordic personal numbers and 30 more, each checked by its check digit, so a mistyped number never links two people, and masked for those who need not see it.

ICON:book

National code systems

SNOMED CT national editions in the country's language, ICD-10-GM and OPS, CIM-10 FR, the UK's ICD-10 and OPCS-4, WHO ICD-10 and ICD-11, each version in force from its effective date.

ICON:shield

GDPR and UK GDPR

Find everything held about a person, give them a copy, erase it with a second person's approval or keep it under a legal hold, and produce the record of processing from the channels.

ICON:server

Data that stays put

Perfuse refuses a channel whose cloud connector is outside the regions allowed, and the hosting templates keep the server, database, backups, logs and keys in Frankfurt, Ireland or London.

Analytics and quality

FHIR as tables, and measures scored where the data lives

What it is

SQL on FHIR turns FHIR resources into rows and columns any SQL tool can read. A digital quality measure counts which patients meet a standard of care, as CMS and NCQA are moving to.

Why it exists

Analysts know SQL, not FHIR. And quality numbers are usually computed weeks later, somewhere else, from a copy of the data.

How you use it

Open SQL on FHIR in the console, pick or write a view, and download CSV or Parquet. Open Quality measures, pick a measure and a period, and read the populations, the score and the patients.

  • SQL on FHIR v2 ViewDefinitions on Perfuse's own FHIRPath engine: all 144 official tests pass
  • CSV, NDJSON and Parquet (read back by DuckDB); $sql-run on the FHIR endpoint and perfuse sof
  • Measures with FHIRPath criteria; Measure/$evaluate-measure and perfuse measure; MeasureReports that pass the Da Vinci DEQM 5.0.0 profiles
  • Not yet: published CMS eCQMs, which are written in CQL and need a CQL engine

AI agents

Let an assistant look, without giving it the keys

What it is

A built-in Model Context Protocol (MCP) server, so AI assistants and agents can search messages, the FHIR store, queues and channel status.

Why it exists

"Why did last night's lab feed stop?" is a question an assistant can answer in seconds, if it can see the engine, and only what it should.

How you use it

Switch MCP on in Settings, create a machine credential under Users, and point the agent at /mcp.

  • Every call runs under the token's own role, channel groups and tenant
  • Read-only by default; writes need both a scope and the role; message bodies hidden from monitor accounts
  • Every tool call written to the audit log, with rate limits

Running it

One file, every platform

What it is

Perfuse is a single program of about 60 MB with the web console inside it. There is no Java to install and no application server.

Why it exists

The fewer moving parts an engine has, the fewer things break during an upgrade, and the smaller the machine it needs.

How you use it

Download it, run perfuse serve, open the console. perfuse init installs it as a service on Linux, macOS or Windows.

  • Linux, macOS and Windows, on Intel and Arm, plus a container image
  • 45 MB of memory at rest, against Mirth Connect's 383 MB
  • Several organisations on one engine, isolated from each other (multi-tenant), each with its own limits on channels, messages a minute and storage
  • Settings that need a restart are applied with a button in the console
  • Also a Go library, for teams who want HL7 parsing in their own programs
